# Orbis build and migration rehearsal

The source tree builds and passes unit, browser-fixture, clean-install Docker, disposable-app lifecycle, and a synthetic stock CLI migration rehearsal. It has **not** passed migration against a copy of an existing homelab. Do not use it to replace a live Runtipi installation yet.

## Rehearse import on a copy

Runtipi's own folders and database are the import format. The fork keeps the original app/store/lifecycle services; there is no importer that guesses or rewrites app definitions. A successful import means the fork starts against an **isolated, consistent copy** of the installation tree and Postgres data, runs its normal migrations, and shows the same users, app URNs, stores, configuration, and app data. The Runtipi v4.10.1 CLI install uses top-level `apps`, `app-data`, `state`, and other data folders plus `data/postgres`. This differs from this repository's development Compose file, which uses `.internal` and a `pgdata` volume.

1. Capture a consistent source snapshot and database backup under an approved procedure. Include any custom `RUNTIPI_*_PATH` mounts, `.env`, Traefik state, app data, user config, media, and backups. For a CLI installation, include `data/postgres`; for a source Compose stack, include the Docker `pgdata` volume, which is **not** part of `.internal`.
2. Restore these into the disposable VM only. The same paths must resolve inside the VM's Compose configuration. The fork and stock core must never use the same database or Docker daemon at once.
3. Run `python3 scripts/migration-preflight.py /path/to/copied/runtipi` against the copied installation. It identifies the CLI or source Compose layout and reports only presence and counts; it does not print `.env` values, follow external path overrides, query Docker, import files, or validate Postgres. A copied CLI `.env` whose `ROOT_FOLDER_HOST` still points at the original location now requires review. Absolute `RUNTIPI_*_PATH` values may also point outside the copy. Resolve every review item before booting the fork.
4. Record before/after hashes for the copied files and database row counts, then boot the fork in the VM. Check every installed app identity, generated/user Compose override, bind mount, external network, URL, secret-dependent setting, and custom store. Exercise backup/restore and a rollback to the stock v4.10.1 image using the untouched snapshot.
5. Treat a migrated installation as verified only when its applications run and can be launched through their actual URLs. A successful UI render or health endpoint alone does not establish compatibility.

For a copied CLI v4.10.1 installation, `python3 scripts/orbis-release-plan.py /path/to/copied/runtipi /path/to/release-manifest.json` validates a reviewed Orbis digest manifest and asks Docker Compose to merge the existing stack, `user-config/tipi-compose.yml` when present, and a proposed Orbis core image override. It reports the image configured by those Compose files and checks that the candidate changes nothing beyond the core image/build identity. It does not inspect the running Docker container, print generated environment values, pull images, start containers, or write the override. This plan is a prerequisite for a migration rehearsal, not an installer.

After taking a separate, verified snapshot of the copied installation, `python3 scripts/orbis-stage-release.py /path/to/copied/runtipi /path/to/release-manifest.json --write` stages the digest-pinned image in `orbis-compose.yml`. With no `--write`, it prints the plan only. It refuses to overwrite a custom `orbis-compose.yml` or a symlink and preserves `user-config/tipi-compose.yml`. The isolated stock CLI copy was staged with the published beta 1 manifest and the merged configuration remained valid. Staging does **not** pull or start an image, stop applications, snapshot Postgres, verify a running container, or roll back. Those steps remain required before a live installation.

### Host command for an adopted installation

`scripts/orbis-host.py` operates a CLI v4.10.1 installation **after** a manually rehearsed Orbis cutover. Its `status` command reports the observed core image and health against a reviewed manifest. `enroll` records a currently healthy, exact digest-pinned Orbis core and hashes the base Compose file, `.env`, user override when present, and generated Orbis override. `stop` stops only the core and reverse proxy. `start` uses the files in base → user → Orbis order, refuses builds and image pulls, waits for health, and never removes app containers as orphans. The selected Docker context and the resolved installation root must be explicit on mutating commands.

For the disposable CLI copy used above, the command sequence was:

```sh
python3 scripts/orbis-host.py status ROOT RELEASE_MANIFEST --docker-context colima-runtipi-test
python3 scripts/orbis-host.py enroll ROOT RELEASE_MANIFEST --docker-context colima-runtipi-test --confirm-root ROOT
python3 scripts/orbis-host.py stop ROOT RELEASE_MANIFEST --docker-context colima-runtipi-test --confirm-root ROOT
python3 scripts/orbis-host.py start ROOT RELEASE_MANIFEST --docker-context colima-runtipi-test --confirm-root ROOT
```

Replace `ROOT` with the exact resolved absolute root in each command. The published beta 3 image passed this enrolled stop/start cycle in the isolated VM; the final status again reported the expected digest and healthy core. The command refuses a changed Compose or environment file and will not enroll a stock core. It is not an installer, first cutover command, updater, snapshot tool, or rollback tool. The adoption and update transactions above handle their respective host operations; real-data validation is still needed before a homelab can be replaced.

## Later Hades cutover

Hades remains untouched during current development. Before the requested second-phase cutover, the exact installed Runtipi version, Compose file, environment, mount overrides, Postgres data, app list, and running services must be inventoried live. After rehearsal on a consistent copy passes, prepare a complete snapshot, record current image digests, quiesce only the stock core, deploy the tested fork with the same data layout, verify the applications and external access, and keep the stock image and snapshot ready for rollback. Never run both cores on the same live data at the same time.

The stock `scripts/install.sh` downloads official Runtipi releases, so it is **not** the fork deployment path. The Settings screen distinguishes upstream core releases from this fork; app-store refresh remains a separate operation. Fork updates must be built from reviewed source and applied through a guarded, reversible procedure.

The pinned Runtipi CLI's `start` command also regenerates `docker-compose.yml`, pulls `ghcr.io/runtipi/runtipi`, removes the core containers, and starts Compose without `orbis-compose.yml`. Its `update` command downloads an upstream release and invokes that same start path. Running either command after an Orbis cutover would replace the Orbis core. A production installer must retire the stock CLI's operational role in favor of Orbis-owned host commands that always include the digest-pinned override. The first-adoption and update transactions are parts of that path, but safe handling of running apps and external data and real-data validation are outstanding. See the pinned [CLI start source](https://github.com/runtipi/cli/blob/v4.10.1/internal/commands/start.go) and [CLI update source](https://github.com/runtipi/cli/blob/v4.10.1/internal/commands/update.go).

A restricted browser-to-host update bridge is now in source; its preview setup and verification limits are in [HOST-SERVICE.md](HOST-SERVICE.md). Its socket path and browser review/install path have completed published-image updates in the isolated Linux VM. It is not yet a supported production installer or package updater.

## Orbis release packaging

The tag workflow in [.github/workflows/release.yml](.github/workflows/release.yml) publishes an Orbis-owned multi-architecture image and a GitHub Release containing its digest manifest and tag-specific notes. It cannot run until `releases/<tag>.md` exists and CI plus integration tests pass. The inherited nightly, upstream CLI, and upstream installer release jobs have been removed. Image publication alone does not install an update; the controller, backup, rollback, and copied-data rehearsal remain outstanding.

`python3 scripts/orbis-release-check.py v0.1.0-beta.4` checks a specific public release without changing the installation. It requires the GitHub release and manifest tag to agree, resolves the Git tag to the manifest commit, hashes the exact GHCR image index, compares the registry digest header, and requires linux/amd64 and linux/arm64 entries. It returns the release notes and digest-pinned image. This check passed against beta 4. It does not prove the images boot on both architectures or apply an update.
