# Orbis build and migration rehearsal

The source tree builds and passes unit, browser-fixture, clean-install Docker, disposable-app lifecycle, and a synthetic stock CLI migration rehearsal. It has **not** passed migration against a copy of an existing homelab. Do not use it to replace a live Runtipi installation yet.

## Verified clean-install smoke test (15 October 2026)

An isolated Colima Linux VM with its own Docker socket built the Orbis image from this tree. The test Compose project used a fresh Postgres volume, loopback-only ports 18080/18443/18081, and no published Postgres port. The image and dependencies started healthy; `/api/health` returned 200. A fresh account registered through the real browser, completed the welcome step, and opened Workspace, Monitor, Updates, App Store, Applications, and Settings without page errors or horizontal overflow at 1440 × 900. The official store was present and the marketplace search reported 248 entries. Unauthenticated telemetry and desktop-preference reads returned 401; authenticated reads and preference save/reload succeeded. [Live screenshots](screenshots/live-smoke) and the repeatable [smoke script](scripts/live-smoke.cjs) capture this check. The script registers a new first user and therefore accepts only a loopback test stack with an empty database.

That first check verifies clean startup and key read paths. The separate app lifecycle check below covers one disposable application. No existing Runtipi data was imported. Host operating system updates and browser-driven Orbis core updates are scoped in [UPDATES.md](UPDATES.md) and are not implemented yet.

## Verified disposable app lifecycle (15 October 2026)

The same isolated VM was reset to an empty database and ran `ORBIS_SMOKE_LIFECYCLE=1 node scripts/live-smoke.cjs`. It installed the official Whoami app, reached running state, stopped, started, restarted, created and listed a backup, reset, restored that backup, and uninstalled while removing the archive. All operations completed through the authenticated browser API, and no application container remained. This verifies one small app on a clean installation; app updates, custom stores, external URLs, TOTP, HTTPS routing, and real existing-install data remain untested.

## Synthetic stock CLI migration and rollback (15 October 2026)

In the isolated Colima VM, the pinned Runtipi CLI v4.10.1 Compose template started the official `ghcr.io/runtipi/runtipi:v4.10.1` image with synthetic credentials, top-level data folders, `data/postgres`, and a `user-config/tipi-compose.yml` override for a loopback test port. A user registered, the official store loaded, and Whoami installed under `whoami:migrated`. With the app and core stopped, the entire installation tree was copied. A local Orbis image replaced only the core image through a final Compose override; the merged Compose model was checked to be otherwise unchanged. Orbis became healthy using the existing database and files, accepted the original session, reported one store and the same running app, then stopped and started that inherited app through its lifecycle API. The core and app were stopped again, the saved installation tree was restored, and stock Runtipi plus the app were recreated. Stock health, the original session, store, and app record all returned; `/api/system/build` returned 404 again as expected for stock.

This verifies the migration path for a small synthetic CLI install and rollback using a full stopped-state copy. It does not validate a copy of Hades, large app data, external paths, user app overrides, custom stores, HTTPS domains, or rollback after an Orbis database migration. The local image was not a published digest-pinned release.

## Isolated core update transaction (15 October 2026)

The host-side `scripts/orbis-host-update.py` now has `plan`, `apply`, and `recover` commands for an **already enrolled** CLI v4.10.1 Orbis installation. It validates the target GitHub Release, manifest, and GHCR image digest; checks the existing enrollment and Compose delta; requires an explicit Docker context; refuses a running managed app; pulls the target image before downtime; stops the four core services; captures a checksum-verified copy of the stopped installation tree; and starts the target digest. A failed start restores the verified tree and previous core. Its transaction journal and snapshot sidecar sit beside the installation rather than inside it. Host commands share a lock so a start/stop cannot overlap an update. The snapshot is an ordinary local copy, not a substitute for an independent backup.

The disposable Colima VM was restored to enrolled beta 4 with synthetic CLI data. `plan` accepted beta 5; `apply` pulled its published arm64 digest, captured 3,518 entries including `data/postgres`, then advanced the core to beta 5. All four core services were healthy, `/api/health` returned 200, the authenticated build API reported the beta 5 tag/commit/digest, and the inherited `whoami:migrated` app record remained. The transaction journal ended at `complete`, and the beta 4 snapshot passed a fresh checksum verification. Unit tests also cover automatic rollback after a failed start, a missing container during failed recreation, interrupted recovery, a corrupted snapshot, a running managed app, and interruption before downtime. This is one small synthetic arm64 installation, not a production update rehearsal with real homelab data.

The `v0.1.0-beta.6` GitHub tag, manifest, and GHCR index then matched commit `985a074d6f5cf536c87fdcbfdb2e58ee7e297a5e` and digest `sha256:b9d62a87fea730b14d8f79e58021c1df644d089f1930a8097a490eb3d54527c9`; both linux/amd64 and linux/arm64 entries were present. The updater advanced the same enrolled synthetic copy from beta 5 to beta 6. Its previous-tree snapshot verified, the four core services became healthy, `/api/health` returned 200, the authenticated build endpoint reported the exact beta 6 tag/commit/digest, and `whoami:migrated` stayed installed. On an isolated, already enrolled copy, use distinct manifests and a new snapshot path outside the installation:

```sh
python3 scripts/orbis-host-update.py plan ROOT CURRENT_MANIFEST TARGET_MANIFEST --docker-context TEST_CONTEXT --snapshot SNAPSHOT
python3 scripts/orbis-host-update.py apply ROOT CURRENT_MANIFEST TARGET_MANIFEST --docker-context TEST_CONTEXT --snapshot SNAPSHOT --confirm-root ROOT
python3 scripts/orbis-host-update.py recover ROOT CURRENT_MANIFEST TARGET_MANIFEST --docker-context TEST_CONTEXT --snapshot SNAPSHOT --confirm-root ROOT
```

`recover` is for an interrupted, nonterminal transaction, not a completed update. The updater currently requires managed apps to be stopped and keeps them stopped. It rejects symlinks outside the installation tree and cannot capture external bind mounts or Docker named volumes outside that tree. It has no first stock-to-Orbis installer, browser API, package-manager adapter, or proven procedure for a real homelab. Large trees may hold the core offline for a long copy and three full-content hash passes; space and downtime must be measured on a representative copy before any live use.

## Isolated Linux test host

Use a disposable Linux VM with its own Docker daemon and no production volumes, network, or Docker context. Runtipi v4.10.1 remains the compatibility base. The fork builds its own `runtipi` image from [Dockerfile](Dockerfile) through [docker-compose.prod.yml](docker-compose.prod.yml); the Compose file's `TIPI_VERSION` is set to `4.10.1` for app compatibility. Keep the source revision and resulting image digest together in test records.

1. Copy this repository into the disposable VM. Check that `docker context show` identifies that VM's own daemon.
2. Create `.env` from `.env.example` and fill the settings required by the test VM. Do not copy Hades credentials or volumes for the initial clean-install run.
3. Run `docker compose --project-name runtipi -f docker-compose.prod.yml config` and review the merged mounts, ports, and network names before starting anything.
4. Run `docker compose --project-name runtipi -f docker-compose.prod.yml up --build -d` in the test VM. The base Compose file publishes ports 80, 443, 8080, and 5432, so keep this VM isolated and verify these bindings suit its network.
5. Confirm `/api/health`, registration/login, TOTP, official and custom store refresh, a disposable app install/update/start/stop/restart/reset/uninstall, backup/restore, custom app and link management, HTTPS routing, and the new authenticated telemetry/preferences endpoints. Verify failures and reconnect behavior as well as success.
6. Record `docker compose ps`, targeted service logs, browser results, and the image digest. Remove only this disposable test environment after collecting the evidence.

## Rehearse import on a copy

Runtipi's own folders and database are the import format. The fork keeps the original app/store/lifecycle services; there is no importer that guesses or rewrites app definitions. A successful import means the fork starts against an **isolated, consistent copy** of the installation tree and Postgres data, runs its normal migrations, and shows the same users, app URNs, stores, configuration, and app data. The Runtipi v4.10.1 CLI install uses top-level `apps`, `app-data`, `state`, and other data folders plus `data/postgres`. This differs from this repository's development Compose file, which uses `.internal` and a `pgdata` volume.

1. Capture a consistent source snapshot and database backup under an approved procedure. Include any custom `RUNTIPI_*_PATH` mounts, `.env`, Traefik state, app data, user config, media, and backups. For a CLI installation, include `data/postgres`; for a source Compose stack, include the Docker `pgdata` volume, which is **not** part of `.internal`.
2. Restore these into the disposable VM only. The same paths must resolve inside the VM's Compose configuration. The fork and stock core must never use the same database or Docker daemon at once.
3. Run `python3 scripts/migration-preflight.py /path/to/copied/runtipi` against the copied installation. It identifies the CLI or source Compose layout and reports only presence and counts; it does not print `.env` values, follow external path overrides, query Docker, import files, or validate Postgres. A copied CLI `.env` whose `ROOT_FOLDER_HOST` still points at the original location now requires review. Absolute `RUNTIPI_*_PATH` values may also point outside the copy. Resolve every review item before booting the fork.
4. Record before/after hashes for the copied files and database row counts, then boot the fork in the VM. Check every installed app identity, generated/user Compose override, bind mount, external network, URL, secret-dependent setting, and custom store. Exercise backup/restore and a rollback to the stock v4.10.1 image using the untouched snapshot.
5. Treat a migrated installation as verified only when its applications run and can be launched through their actual URLs. A successful UI render or health endpoint alone does not establish compatibility.

For a copied CLI v4.10.1 installation, `python3 scripts/orbis-release-plan.py /path/to/copied/runtipi /path/to/release-manifest.json` validates a reviewed Orbis digest manifest and asks Docker Compose to merge the existing stack, `user-config/tipi-compose.yml` when present, and a proposed Orbis core image override. It reports the image configured by those Compose files and checks that the candidate changes nothing beyond the core image/build identity. It does not inspect the running Docker container, print generated environment values, pull images, start containers, or write the override. This plan is a prerequisite for a migration rehearsal, not an installer.

After taking a separate, verified snapshot of the copied installation, `python3 scripts/orbis-stage-release.py /path/to/copied/runtipi /path/to/release-manifest.json --write` stages the digest-pinned image in `orbis-compose.yml`. With no `--write`, it prints the plan only. It refuses to overwrite a custom `orbis-compose.yml` or a symlink and preserves `user-config/tipi-compose.yml`. The isolated stock CLI copy was staged with the published beta 1 manifest and the merged configuration remained valid. Staging does **not** pull or start an image, stop applications, snapshot Postgres, verify a running container, or roll back. Those steps remain required before a live installation.

### Host command for an adopted installation

`scripts/orbis-host.py` operates a CLI v4.10.1 installation **after** a manually rehearsed Orbis cutover. Its `status` command reports the observed core image and health against a reviewed manifest. `enroll` records a currently healthy, exact digest-pinned Orbis core and hashes the base Compose file, `.env`, user override when present, and generated Orbis override. `stop` stops only the core and reverse proxy. `start` uses the files in base → user → Orbis order, refuses builds and image pulls, waits for health, and never removes app containers as orphans. The selected Docker context and the resolved installation root must be explicit on mutating commands.

For the disposable CLI copy used above, the command sequence was:

```sh
python3 scripts/orbis-host.py status ROOT RELEASE_MANIFEST --docker-context colima-runtipi-test
python3 scripts/orbis-host.py enroll ROOT RELEASE_MANIFEST --docker-context colima-runtipi-test --confirm-root ROOT
python3 scripts/orbis-host.py stop ROOT RELEASE_MANIFEST --docker-context colima-runtipi-test --confirm-root ROOT
python3 scripts/orbis-host.py start ROOT RELEASE_MANIFEST --docker-context colima-runtipi-test --confirm-root ROOT
```

Replace `ROOT` with the exact resolved absolute root in each command. The published beta 3 image passed this enrolled stop/start cycle in the isolated VM; the final status again reported the expected digest and healthy core. The command refuses a changed Compose or environment file and will not enroll a stock core. It is not an installer, first cutover command, updater, snapshot tool, or rollback tool. The separate update transaction above is available only for an already enrolled installation; a restricted host service and real-data validation are still needed before the browser can apply releases or a real homelab can be replaced.

## Later Hades cutover

Hades remains untouched during current development. Before the requested second-phase cutover, the exact installed Runtipi version, Compose file, environment, mount overrides, Postgres data, app list, and running services must be inventoried live. After rehearsal on a consistent copy passes, prepare a complete snapshot, record current image digests, quiesce only the stock core, deploy the tested fork with the same data layout, verify the applications and external access, and keep the stock image and snapshot ready for rollback. Never run both cores on the same live data at the same time.

The stock `scripts/install.sh` downloads official Runtipi releases, so it is **not** the fork deployment path. The Settings screen distinguishes upstream core releases from this fork; app-store refresh remains a separate operation. Fork updates must be built from reviewed source and applied through a guarded, reversible procedure.

The pinned Runtipi CLI's `start` command also regenerates `docker-compose.yml`, pulls `ghcr.io/runtipi/runtipi`, removes the core containers, and starts Compose without `orbis-compose.yml`. Its `update` command downloads an upstream release and invokes that same start path. Running either command after an Orbis cutover would replace the Orbis core. A later installer must retire the stock CLI's operational role in favor of Orbis-owned host commands that always include the digest-pinned override. The update transaction is one part of that path, but initial cutover, safe handling of running apps and external data, and browser authorization are outstanding. See the pinned [CLI start source](https://github.com/runtipi/cli/blob/v4.10.1/internal/commands/start.go) and [CLI update source](https://github.com/runtipi/cli/blob/v4.10.1/internal/commands/update.go).

## Orbis release packaging

The tag workflow in [.github/workflows/release.yml](.github/workflows/release.yml) publishes an Orbis-owned multi-architecture image and a GitHub Release containing its digest manifest and tag-specific notes. It cannot run until `releases/<tag>.md` exists and CI plus integration tests pass. The inherited nightly, upstream CLI, and upstream installer release jobs have been removed. Image publication alone does not install an update; the controller, backup, rollback, and copied-data rehearsal remain outstanding.

`python3 scripts/orbis-release-check.py v0.1.0-beta.4` checks a specific public release without changing the installation. It requires the GitHub release and manifest tag to agree, resolves the Git tag to the manifest commit, hashes the exact GHCR image index, compares the registry digest header, and requires linux/amd64 and linux/arm64 entries. It returns the release notes and digest-pinned image. This check passed against beta 4. It does not prove the images boot on both architectures or apply an update.
