# Orbis resource monitoring

`GET /api/system/containers` requires the existing authenticated session or CLI guard. The backend uses its existing Docker connection; the browser receives selected readings only. Container inspection data, environment variables, healthcheck logs, commands, filesystem mounts, and the Docker socket are not returned.

The sampler shares one result across viewers for five seconds, coalesces concurrent requests, limits Docker calls to four containers at a time, and aborts a sample after four seconds. It includes up to 200 containers and reports any omitted count. Sampling is requested by visible browser views and pauses in background tabs. It keeps only the previous CPU counters in memory.

CPU follows [Docker Engine's delta calculation](https://docs.docker.com/reference/api/engine/version/v1.51/): 100% represents one CPU core, so multi-core workloads can exceed 100%. The first one-shot reading may need another sample before CPU can be calculated. Memory subtracts reclaimable inactive file cache, with a cgroup v1 cache fallback. Network and block I/O values are cumulative container counters. Missing or unsupported values remain unavailable.

App containers are associated through `runtipi.appurn`, or the existing Compose project name for older installations. Multi-container app health is conservative: an unhealthy service takes precedence, a restarting/starting service remains starting, a partly stopped app is labelled partly stopped, and only all-running, all-healthy checked containers produce “Healthy.” Running containers without configured healthchecks are labelled “No healthcheck.”

The workspace combines CPU, memory, container network, and runtime storage in System status. Home and Monitor show uptime from the existing system telemetry instead of the sample timestamp, formatted as days, hours and minutes. With the host-proc mount configured, the collector reads the server's `/proc/uptime`; it does not count how long the Orbis container has been running. On the owned Linux test host, API and host uptime differed by 1.56 seconds before the beta 27 update.

The Usage section and expanded Monitor rank containers by CPU or memory, highest first. This ranking covers Docker workloads only; it does not claim to identify other host processes. Sensor telemetry and host-process ranking remain future work.

## Host devices

Beta42 adds authenticated `GET /api/system/host-telemetry` and Monitor's Host devices section. The existing restricted Linux helper exposes only a fixed, zero-argument `GET /v1/telemetry` on its private Unix socket. A missing helper, older helper or unavailable capability remains explicit; Orbis core-container capacity/network readings retain their separate headings. This requires the updated helper and core; the older beta41 core does not include this feature.

Mounted filesystem capacity comes from host `statvfs`, not the container's mount namespace. The list skips kernel/in-memory filesystems and temporary container overlay mounts, preserving the host root even on an overlay-based host. Mount source and option fields are never returned because they can contain credentials. Available capacity can differ from total minus used because filesystems reserve space. Bind mounts can share capacity; their values are not added into a fake total.

Interface totals come from `/proc/net/dev`; link state, link speed and identity come from selected sysfs files. Loopback is excluded. Whole-device I/O comes from `/proc/diskstats`, excluding partitions and loop/ram/CD devices. Read/write rates use actual monotonic elapsed time and [Linux's fixed 512-byte counter sectors](https://docs.kernel.org/block/stat.html). Active time follows the kernel I/O-time counter and is approximate, especially with concurrent I/O; it is not a claim of drive saturation. Layered devices can share the same traffic, so no aggregate is fabricated. Counter resets, replaced device identities, the first sample and gaps over 60 seconds produce unavailable rates until two recent samples exist. [Kernel counter definitions](https://docs.kernel.org/admin-guide/iostats.html) describe these limits.

One shared daemon worker samples on demand at most every ten seconds. Each counter file read is bounded, each group exposes at most 32 items, omitted counts and partial failures are explicit, and only previous counter sets plus the latest snapshot remain in memory. A blocked filesystem cannot block HTTP handlers or spawn more sampler workers; existing values become stale after 30 seconds. The backend coalesces viewers, validates and selects every returned field, caps the response at 256 KiB and ends a socket request after two seconds. Browser polling stops in background/minimized views; a first Collecting response retries after two seconds, then normal reads use ten seconds.

Monitor uses readable directory-boundary wrapping, with full-text/title ellipsis for unusually long individual identifiers. Facts reflow as text grows. Automatic refresh preserves reading position. Successful Retry restores keyboard focus to the surviving Host devices heading, using only the minimum padded scroll adjustment when that target is behind the chrome. It does not move focus away from another control the user selected.

The retained Linux source probe uses only the owned arm64 Colima guest, a temporary Unix server and two real samples; it never updates the installed helper/core. A separate installed-helper probe verifies the reviewed helper upgrade, actual host/core Unix reads, two distinct samples, source hashes and private permissions at the pre-OTA beta41 boundary. The subsequent reviewed beta42 OTA and independent stopped snapshot/data verification pass. API authentication/transport/counter fixtures and the compiled-source UI matrix remain separate evidence; the actual published beta42 API/render audit also passes five native/enlarged layouts with real 11/8/3 device groups, separate unauthenticated 401, authenticated 200 and ten-second refreshes preserving exact scroll. [Actual captures and assertions](screenshots/live-beta42/README.md) record its read-only scope, unchanged records, loaded assets and closed browser resources. Hades is untouched.

## Host process rankings (source after beta42)

Authenticated `GET /api/system/host-processes` reads only the fixed, zero-argument `GET /v1/processes` on the private helper socket. Older or missing helpers report the missing capability without exposing raw errors. The new helper module is `orbis-host-processes.py`; core updates do not replace that installed module. The Monitor presentation is being checked separately; published beta42 does not include process rankings.

The collector reads only numeric, canonical `/proc/PID/stat` entries. It selects PID, printable process name, CPU time and resident memory; it never reads command arguments, environment, executable links or process-owner details and has no signal/control operation. CPU compares user plus system clock ticks for the same PID/start time across actual monotonic intervals of 2–60 seconds. 100% is one CPU core; multi-threaded processes can exceed it. New/reused PIDs, counter resets and long gaps wait for another sample. RSS uses the host page size and is approximate; shared pages and container processes overlap other readings, so totals are not fabricated. [Linux stat definitions](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html) and [kernel RSS accounting](https://docs.kernel.org/filesystems/proc.html) describe these semantics.

At most 8,192 processes and one second of scan work are attempted per sample, with a 4 KiB bound per stat file. A single on-demand daemon worker runs at most once every ten seconds, independently of filesystem probes. It retains bounded prior counters and top-20 heaps for CPU and memory, ordered highest first with PID ties. Unreadable/exited processes and limited scans remain explicit. The first memory sample is usable immediately; CPU waits for a comparison. Old samples become stale after 30 seconds. The backend shares requests, validates counts/order/identities, selects fields, caps responses at 256 KiB and ends requests after two seconds. A two-second warming cache exposes the first CPU comparison promptly, then ready reads share ten seconds.

[Actual Linux source proof and limits](screenshots/host-processes/README.md) record 123 real process reads, controlled CPU attribution and independent RSS verification without changing the installed helper/core. Source tests and temporary-handler checks do not establish published-image acceptance. Hades is untouched.

## Recorded history

`GET /api/system/history?range=5m|1h|24h|7d` requires the same authentication guard. Other values, including repeated query parameters, are rejected. The backend samples the existing shared system collector every ten seconds, even without a browser connected. It does not run background Docker inspections for history. Browser history requests stop in background tabs and share a single query across the four charts.

The latest hour has at most 360 individual samples in memory. Seven days of minute aggregates contain only timestamps, source scope, counts, sums and peaks for CPU, host memory usage, and core-container network rates. Each metric has its own valid-sample count; missing values remain missing. A CPU source change within an aggregate makes that aggregate's CPU value unavailable, so host and core CPU readings are never averaged together.

Minute summaries append to `/data/state/orbis-metrics/minutes-v1.jsonl` in a private directory (`0700`, journal `0600`). The journal is compacted atomically about once an hour; expired rows can remain on disk until that compaction, while API ranges and memory are pruned to seven days. Reads reject files above 8 MiB, excessive record counts, invalid timestamps and impossible aggregates. At most 10,081 minute buckets are retained in memory, and API output is capped at 720 points. Minute appends avoid rewriting a multi-day file for every reading.

On graceful shutdown, the current partial minute is flushed through Nest's shutdown hooks. A forced kill can lose up to the current unsaved minute; `persistedThrough` identifies the last successful save. A valid journal reloads on restart. Corrupt storage is preserved, valid earlier rows remain readable, and collection continues in bounded memory with an explicit storage warning. A write failure also keeps current readings available and attempts a later compacted checkpoint.

The 5-minute view uses recent individual readings with saved minute summaries before the current process's recent buffer. Longer ranges use sample-weighted 1-minute, 5-minute and 30-minute averages, retaining peaks and counts for inspection. Averages describe actual samples, not an assumption of continuous coverage. No samples are created for downtime. The charts use real time coordinates, break lines across missing readings, collection gaps and CPU source changes, and label the selected time range. Pointer inspection and Left/Right/Home/End keyboard controls reveal timestamps, averages, peaks and source labels.

History currently covers aggregate CPU, host memory, and core-network rates. It does not record per-container history, host disk throughput, or sensors. Current per-container readings remain available separately.

Chart axes size to their labels instead of using a fixed pixel allowance. Time labels wrap when space is limited. Inspection details appear in the document flow below the plot so enlarged text does not cover subsequent core rows; keyboard Left/Right/Home/End and the slider's complete value description remain available.
