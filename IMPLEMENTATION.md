# Orbis implementation and deployment record

## Base and compatibility

This fork starts from Runtipi `v4.10.1`, commit `5734817389df55aafb9afd571e42e12ab7e647e0` (10 June 2026). The upstream project is GPL-3.0; `LICENSE` is retained. The repository is a Bun workspace: React Router frontend, Nest backend, Postgres, RabbitMQ, Traefik, Dockerode, generated OpenAPI client, and the official/custom store mechanism.

The visible product name, browser title, manifest, logo, and primary screens are Orbis. Internal Compose service names, package imports, API routes, and `RUNTIPI_*` environment keys retain their upstream names to keep existing installations and app definitions compatible. Hades remains only the editable default server display name.

Runtipi already provides authenticated application lifecycle, official and custom stores, dynamic install forms, custom apps, links, logs, backup/restore, reset, and system settings. Their routes and APIs remain the compatibility contract. The desktop work must not replace app definitions or duplicate app configuration.

## Phases

1. Replace the authenticated shell, dashboard, installed-app and store presentation. Keep existing action components and backend routes. Add a focused system monitor using real readings.
2. Complete server-persisted workspace and appearance settings, richer host telemetry, task history, window behavior, and accessibility/browser checks.
3. Validate a migration against a *copy* of a real Runtipi data tree in a disposable Linux VM and isolated Docker daemon. Check app URNs, stores, user config overrides, app data, database migrations, auth, Traefik, backup/restore, and rollback.
4. Only after explicit approval, take a Hades snapshot/backup, quiesce stock Runtipi, deploy the fork against the existing mount layout, verify every app and config, and retain a tested rollback path. No Hades changes occur in phases 1-3.

A later multi-homelab controller/agent phase is recorded in [MULTI-HOMELAB.md](MULTI-HOMELAB.md). It is intentionally downstream of single-server compatibility and migration validation.

The requested browser Update Center for apps, Orbis releases, and host packages is scoped in [UPDATES.md](UPDATES.md). Host updates require a restricted host helper and disposable-host validation before browser controls can apply them.

## Current implementation

- Authenticated server desktop shell with a responsive top bar, dock, first-party routes, keyboard tool and installed-app search, and logout through the existing API.
- Workspace populated from Runtipi's installed-app and links APIs plus the authenticated telemetry endpoint shared with Monitor. It labels host CPU and memory, core-container network, and runtime filesystem readings. App and store detail links keep their original routes and lifecycle components.
- Explicit Workspace edit mode for the four current widgets. A user can show, hide, reorder, choose standard or wide width, and restore the layout through visible keyboard-operable buttons. Up to 12 installed applications can be pinned to the front of the launch area. Layout and pins are saved per user with appearance preferences; old saved files load with the default layout.
- System Monitor uses a new authenticated `/api/system/telemetry` endpoint for current per-core CPU, host-mounted memory and swap, runtime filesystems, and runtime network interfaces. Unavailable readings stay unavailable. The server shares each sample for four seconds and coalesces concurrent probes, limiting work when multiple browsers are open. Live charts keep at most 60 samples in the open browser view; there is no fabricated or persisted history.
- New per-user desktop appearance endpoint under `/api/desktop-preferences`, protected by Runtipi's `AuthGuard` and request validation. Data is stored under the existing `/data/state/desktop` mount, with browser caching and export/import of non-secret settings.
- Three bundled original SVG wallpapers and six appearance presets, with saved per-user selection. Login, app list, store, settings, and detail routes sit within the shared visual shell.
- Update Center shows installed-app update availability using existing store metadata and reads published Orbis release notes from GitHub. It labels host package updates unavailable and keeps core installation disabled unless the restricted host service is connected to a healthy enrolled installation.
- A restricted host service and authenticated browser routes for Orbis core update plan/apply/recovery are now in source. The Update Center shows the exact digest and snapshot estimate before installation. Published browser updates through beta 13, Linux socket mount, systemd restart, VM reboot, first-install helper setup, and an in-place helper upgrade with injected-failure rollback passed on synthetic data. The beta 12 → beta 13 core update used the upgraded helper. Production use still needs a copied real-data rehearsal and external-mount handling. See [HOST-SERVICE.md](HOST-SERVICE.md).
- Stock per-app reset, backup/restore, custom store, custom app, dynamic install form, and lifecycle code has not been removed.

## Current limits

- This is an implemented first slice, not yet a drop-in Runtipi replacement. The store and detail flows still need deeper visual work; task history, window controls, application groups and recent-use ordering, expanded monitoring, wallpaper upload, and advanced theme controls are pending. Widget editing currently covers four fixed widgets with button controls; drag positioning and additional widget types remain open.
- The inherited `/system/load` endpoint reports CPU and filesystem data from the Runtipi runtime; the new workspace uses `/system/telemetry` instead. That endpoint reports host CPU and memory when the read-only proc mounts exist, while filesystem and network detail still describe the Orbis core container. Host-wide disks/network, temperatures, fans, GPU, container telemetry, and historical storage still need explicit host mounts or an agent design.
- Browser screenshots include labelled development fixtures and a clean-install run against an isolated Colima Docker daemon. The latter verified registration, welcome, main routes, authenticated telemetry/preferences, and a 248-entry official catalogue. A disposable Whoami lifecycle and a synthetic stock CLI migration/rollback have since passed. Migration of real homelab data remains untested.
- The official app-store connection uses the unchanged Runtipi mechanism. Catalogue search and one official Whoami install/uninstall path were verified on the clean install; app updates and custom-store refresh still need disposable-daemon checks.

## Compatibility and import design

The fork keeps the Runtipi data directory layout (`apps`, `app-data`, `user-config`, `repos`, `state`, `backups`, `traefik`, `media`, and logs) and the Runtipi Postgres database. Existing config should therefore be read by the original services when the same volumes and database are mounted. This is the intended automatic import path, not yet a verified migration. It requires a compatible database migration and must first be rehearsed against a copy. Do not point two live Runtipi cores at the same data or Docker daemon concurrently. Do not treat a filesystem copy alone as a successful import.

The rehearsal must include Hades's `migrated` app identities, generated and user Compose files, `user-config` overrides, app-data bind mounts, encrypted settings, custom stores, Postgres volume, `.env`, Traefik state, and external networks. Compare file hashes and database row counts before and after. Test rollback with a preserved image and data snapshot before cutover.

`scripts/migration-preflight.py` can inventory an isolated copy of a Runtipi installation without printing `.env` values or reading Docker state. It does not import data or validate the separate Postgres named volume. External data path overrides are flagged for manual review rather than followed outside the copy. `scripts/orbis-release-plan.py` verifies a reviewed release manifest against the copied CLI Compose model; `scripts/orbis-stage-release.py` writes only a generated core image override after that check. `scripts/orbis-host.py` can enroll and start/stop an already healthy Orbis installation at the same pinned digest. `scripts/orbis-host-update.py` adds a stopped-state snapshot, journal, digest-pinned update, and recovery for an already enrolled CLI installation. `scripts/orbis-host-adopt.py` now performs a guarded first stock v4.10.1 cutover with a verified snapshot and stock rollback; both a successful adoption and an injected post-start failure rollback passed on synthetic data in the isolated VM. These commands do not capture external mounts or named volumes outside the installation tree.

The existing per-app reset action is retained. An instance-wide reset needs a separate, explicitly specified destructive workflow with a verified backup, so it is not implemented by deleting the Runtipi data tree.

## Verification boundary

The macOS development machine uses a project-local Bun runner and an isolated Colima Linux VM for Docker tests. Bun installed dependencies and completed type checks, tests, and production bundles. `scripts/visual-qa.cjs` exercised fixture-based desktop and mobile routes in installed Chrome; it also checked widget reorder, hide, width, app pinning, and persistence on desktop, phone, and a 320px viewport with enlarged editor text. `scripts/live-smoke.cjs` exercised a clean-install browser session and the real APIs against the VM. With `ORBIS_SMOKE_LIFECYCLE=1`, it also completed install, stop, start, restart, backup, reset, restore, and uninstall for the official Whoami app. The authenticated preference and build endpoints passed unit and live checks. A separate synthetic Runtipi CLI install with Whoami and a custom core override booted with local Orbis and returned to stock from a stopped-state copy. The first seven published arm64 beta images were pulled by immutable digest and booted on the synthetic CLI install. Beta 1 launched inherited Whoami through its browser Open control. A local build after beta 2 verified immediate startup reconciliation of an inherited app whose container had stopped. Beta 3 passed an enrolled host-command stop/start cycle on the disposable CLI copy. Beta 4 retained the inherited account, app, store, and telemetry. Beta 5 had a matching GitHub tag, manifest, and GHCR index for amd64 and arm64; its arm64 image booted healthy, and an inherited app pin persisted through the real browser and API. The host update transaction advanced the synthetic installation from beta 4 through beta 7, with verified previous-release snapshots; the inherited app record and authenticated build API remained available. The first-adoption transaction then took a fresh synthetic stock install to published beta 7, retaining its account and Whoami; an injected failure after Orbis start restored the exact stock image and verified data snapshot. A real browser check found that beta 6 still briefly displayed a stale save label after a pin change. A locally built image with the subsequent preference-state fix passed the same interaction, and the published beta 7 image repeated that result with response-backed pin persistence. Later published images reached beta 13. Four browser-clicked core updates passed on the isolated arm64 installation with exact published digests and verified stopped-tree snapshots; the corrected systemd helper survived a VM restart. Chrome checked the released beta 11 changelog and live Monitor, then beta 12 My Apps at 1440px and 390px without horizontal overflow or page errors. Beta 12 also passed constrained-panel and enlarged-scale fixture checks. The in-place helper upgrade then passed failure rollback and served the beta 13 browser update. Migration of actual existing homelab data still requires an isolated consistent copy. Hades is reserved for the later deployment phase.
