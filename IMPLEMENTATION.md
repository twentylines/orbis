# Orbis implementation and deployment record

## Base and compatibility

This fork starts from Runtipi `v4.10.1`, commit `5734817389df55aafb9afd571e42e12ab7e647e0` (10 June 2026). The upstream project is GPL-3.0; `LICENSE` is retained. The repository is a Bun workspace: React Router frontend, Nest backend, Postgres, RabbitMQ, Traefik, Dockerode, generated OpenAPI client, and the official/custom store mechanism.

The visible product name, browser title, manifest, logo, and primary screens are Orbis. Internal Compose service names, package imports, API routes, and `RUNTIPI_*` environment keys retain their upstream names to keep existing installations and app definitions compatible. Hades remains only the editable default server display name.

Runtipi already provides authenticated application lifecycle, official and custom stores, dynamic install forms, custom apps, links, logs, backup/restore, reset, and system settings. Their routes and APIs remain the compatibility contract. The desktop work must not replace app definitions or duplicate app configuration.

## Phases

1. Replace the authenticated shell, dashboard, installed-app and store presentation. Keep existing action components and backend routes. Add a focused system monitor using real readings.
2. Complete server-persisted workspace and appearance settings, richer host telemetry, task history, window behavior, and accessibility/browser checks.
3. Validate a migration against a *copy* of a real Runtipi data tree in a disposable Linux VM and isolated Docker daemon. Check app URNs, stores, user config overrides, app data, database migrations, auth, Traefik, backup/restore, and rollback.
4. Only after explicit approval, take a Hades snapshot/backup, quiesce stock Runtipi, deploy the fork against the existing mount layout, verify every app and config, and retain a tested rollback path. No Hades changes occur in phases 1-3.

A later multi-homelab controller/agent phase is recorded in [MULTI-HOMELAB.md](MULTI-HOMELAB.md). It is intentionally downstream of single-server compatibility and migration validation.

The requested browser Update Center for apps, Orbis releases, and host packages is scoped in [UPDATES.md](UPDATES.md). Host updates require a restricted host helper and disposable-host validation before browser controls can apply them.

## Current implementation

- Authenticated server desktop shell with a responsive top bar, dock, first-party routes, a search surface that expands from the header and covers sections, installed apps and catalogue apps, and logout through the existing API.
- Workspace populated from Runtipi's installed-app and links APIs plus the authenticated telemetry endpoint shared with Monitor. It labels host CPU and memory, core-container network, and runtime filesystem readings. App and store detail links keep their original routes and lifecycle components.
- Explicit Workspace edit mode for the four current widgets. A user can show, hide, reorder, choose standard or wide width, and restore the layout through visible keyboard-operable buttons. Up to 12 installed applications can be pinned to the front of the launch area. A direct picker and saved Show all option control the launcher. More than three visible apps compact the lower cards; all apps scroll inside their pane while either lower card is enabled. Layout and pins are saved per user with appearance preferences; old saved files load with defaults.
- System Monitor uses authenticated current host/runtime telemetry and a shared Docker collector for per-container health, CPU, memory, network totals, and block I/O totals. Workspace and Monitor can rank Docker consumers by CPU or memory. Unavailable readings stay unavailable. A shared ten-second server collector keeps bounded recent samples and seven days of minute summaries, with authenticated time ranges, measured averages/peaks, gap-aware charts and keyboard inspection. History survives navigation and reloads; journal persistence is tested separately from current readings. See [MONITORING.md](MONITORING.md).
- Persistent lifecycle Task centre, system-bar active count, and Recent operations workspace surface. Queue request IDs, phases, and timestamps survive reloads and core restart. Host/core update journals remain separate in Update Center. See [TASKS.md](TASKS.md).
- New per-user desktop appearance endpoint under `/api/desktop-preferences`, protected by Runtipi's `AuthGuard` and request validation. Data is stored under the existing `/data/state/desktop` mount, with browser caching and export/import of non-secret settings.
- Three bundled wallpapers and six appearance presets, with saved light/dark mode and per-user selection. Authenticated app list, store, settings and detail routes use the shared shell; portals and editors use its theme tokens. Dock section slides and the search morph respect reduced motion. Responsive connection status shows the configured server IP.
- Update Center shows installed-app update availability using existing store metadata and reads published Orbis release notes from GitHub. On a connected Ubuntu 24.04 host helper it reads current APT upgrade candidates, repository metadata, reboot request status, and an on-demand distribution changelog. The package worker provides explicit package selection, reviewed APT simulation, a separate systemd install job and status. It labels unsupported or disconnected hosts and keeps core installation disabled unless the restricted host service is connected to a healthy enrolled installation. The published beta 15 browser package rehearsal is recorded in `DEPLOYMENT.md`; real-host deployment remains a separate gate.
- A restricted host service and authenticated browser routes for Orbis core update plan/apply/recovery are now in source. The Update Center shows the exact digest and snapshot estimate before installation. Published browser updates through beta 14, Linux socket mount, systemd restart, VM reboot, first-install helper setup, and an in-place helper upgrade with injected-failure rollback passed on synthetic data. The beta 13 → beta 14 core update used the upgraded helper; the released browser then read real host package candidates and a changelog. Production use still needs a copied real-data rehearsal and external-mount handling. See [HOST-SERVICE.md](HOST-SERVICE.md).
- Shared official/custom application workspaces retain lifecycle, update, install, backup, reset and remove actions. Resources and operation history use the full app URN. Sections follow URL/history/keyboard changes; stale log streams close when their scope changes, and guarded log queries are bounded to 1–1000 lines before streaming headers open.
- Stock custom-store, custom-app and dynamic-form APIs remain the compatibility contract.

The full remaining product scope and evidence requirements are tracked in [ACCEPTANCE.md](ACCEPTANCE.md).

## Current limits

- This is an incomplete product preview, not yet a verified drop-in Runtipi replacement. Remaining inherited edit/update/backup and recovery flows need further acceptance coverage; window controls, application groups and recent-use ordering, expanded host monitoring, wallpaper upload, and full theme packs are pending. Widget editing currently covers four fixed widgets with button controls; drag positioning and additional widget types remain open.
- The inherited `/system/load` endpoint reports CPU and filesystem data from the Runtipi runtime; the new workspace uses `/system/telemetry` instead. That endpoint reports host CPU and memory when the read-only proc mounts exist, while filesystem and network detail still describe the Orbis core container. Host-wide disks/network, temperatures, fans, GPU and host-process detail still need explicit host mounts or an agent design. Container telemetry uses the existing Docker connection; aggregate CPU/memory/core-network history now has bounded local storage.
- Browser screenshots include labelled development fixtures and a clean-install run against an isolated Colima Docker daemon. The latter verified registration, welcome, main routes, authenticated telemetry/preferences, and a 248-entry official catalogue. A disposable Whoami lifecycle and a synthetic stock CLI migration/rollback have since passed. Migration of real homelab data remains untested.
- The official app-store connection uses the unchanged Runtipi mechanism. Catalogue search and one official Whoami install/uninstall path were verified on the clean install; app updates and custom-store refresh still need disposable-daemon checks.

## Compatibility and import design

The fork keeps the Runtipi data directory layout (`apps`, `app-data`, `user-config`, `repos`, `state`, `backups`, `traefik`, `media`, and logs) and the Runtipi Postgres database. Existing config should therefore be read by the original services when the same volumes and database are mounted. This is the intended automatic import path, not yet a verified migration. It requires a compatible database migration and must first be rehearsed against a copy. Do not point two live Runtipi cores at the same data or Docker daemon concurrently. Do not treat a filesystem copy alone as a successful import.

The rehearsal must include Hades's `migrated` app identities, generated and user Compose files, `user-config` overrides, app-data bind mounts, encrypted settings, custom stores, Postgres volume, `.env`, Traefik state, and external networks. Compare file hashes and database row counts before and after. Test rollback with a preserved image and data snapshot before cutover.

`scripts/migration-preflight.py` can inventory an isolated copy of a Runtipi installation without printing `.env` values or reading Docker state. It does not import data or validate the separate Postgres named volume. External data path overrides are flagged for manual review rather than followed outside the copy. `scripts/orbis-release-plan.py` verifies a reviewed release manifest against the copied CLI Compose model; `scripts/orbis-stage-release.py` writes only a generated core image override after that check. `scripts/orbis-host.py` can enroll and start/stop an already healthy Orbis installation at the same pinned digest. `scripts/orbis-host-update.py` adds a stopped-state snapshot, journal, digest-pinned update, and recovery for an already enrolled CLI installation. `scripts/orbis-host-adopt.py` now performs a guarded first stock v4.10.1 cutover with a verified snapshot and stock rollback; both a successful adoption and an injected post-start failure rollback passed on synthetic data in the isolated VM. These commands do not capture external mounts or named volumes outside the installation tree.

The existing per-app reset action is retained. An instance-wide reset needs a separately specified destructive workflow with a verified backup. It remains unimplemented.

## Verification boundary

PR 17 source passed all package types, 307 backend tests and protected build/common/integration gates. Retained Chrome fixtures cover 1440/768/390/320 in both modes, 14-app workspace states, 4K baseline routes and a 2× rendering/zoom-layout simulation. Independent inspections also cover intermediate header/grid widths, native/reduced motion, interrupted search, stale responses, error/retry states and inner padding. `VISUAL-QA.md` records the scope and limits. Published beta 21 completed the reviewed beta 20→21 OTA with an exact digest, healthy enrolled core and retained settings/tasks. Real app resources/logs, the HTTP 400/401 boundary, saved Home controls, installed/catalogue/section search and all 248 icons passed; original preferences and the stopped app state were restored. See `DEPLOYMENT.md` for exact release/task records.

The following records describe earlier isolated rehearsals.

The macOS development machine uses a project-local Bun runner and an isolated Colima Linux VM for Docker tests. With `ORBIS_SMOKE_LIFECYCLE=1`, it also completed install, stop, start, restart, backup, reset, restore, and uninstall for the official Whoami app. The authenticated preference and build endpoints passed unit and live checks. A separate synthetic Runtipi CLI install with Whoami and a custom core override booted with local Orbis and returned to stock from a stopped-state copy. The first seven published arm64 beta images were pulled by immutable digest and booted on the synthetic CLI install. Beta 1 launched inherited Whoami through its browser Open control. A local build after beta 2 verified immediate startup reconciliation of an inherited app whose container had stopped. Beta 3 passed an enrolled host-command stop/start cycle on the disposable CLI copy. Beta 4 retained the inherited account, app, store, and telemetry. Beta 5 had a matching GitHub tag, manifest, and GHCR index for amd64 and arm64; its arm64 image booted healthy, and an inherited app pin persisted through the real browser and API. The host update transaction advanced the synthetic installation from beta 4 through beta 7, with verified previous-release snapshots; the inherited app record and authenticated build API remained available. The first-adoption transaction then took a fresh synthetic stock install to published beta 7, retaining its account and Whoami; an injected failure after Orbis start restored the exact stock image and verified data snapshot. A real browser check found that beta 6 still briefly displayed a stale save label after a pin change. A locally built image with the subsequent preference-state fix passed the same interaction, and the published beta 7 image repeated that result with response-backed pin persistence. Later published images reached beta 13. Four browser-clicked core updates passed on the isolated arm64 installation with exact published digests and verified stopped-tree snapshots; the corrected systemd helper survived a VM restart. Chrome checked the released beta 11 changelog and live Monitor, then beta 12 My Apps at 1440px and 390px without horizontal overflow or page errors. Beta 12 also passed constrained-panel and enlarged-scale fixture checks. The in-place helper upgrade then passed failure rollback and served the beta 13 browser update. Migration of actual existing homelab data still requires an isolated consistent copy. Hades is reserved for the later deployment phase.
