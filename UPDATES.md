# Orbis Update Center: implementation contract

Orbis will make application, Orbis core, and host operating system updates visible in the browser with the release notes that belong to each update. These are separate operations with different permissions and rollback paths.

## Application updates

Keep Runtipi's installed app identities, store metadata, compatibility checks, generated forms, and existing app update service. The Update Center should reuse the current app version and lifecycle APIs, link to each app's configured store entry, and show the store's supplied release notes when present. It must report when a store provides no changelog. App-store refresh must never replace the Orbis core image.

## Orbis releases

Use GitHub Releases from the Orbis repository as the changelog source. Show the installed commit/image digest, available release tag, publication time, release notes, and whether a compatible image is available. The browser can check releases without credentials for a public repository, but applying a release must use a reviewed image digest and a server-side deployment controller with a backup and rollback path. The stock `scripts/install.sh` downloads upstream Runtipi and must not be presented as an Orbis updater.

The upstream Runtipi CLI `start` and `update` paths also pull and run the upstream core without Orbis's Compose override. A production Orbis install must have an Orbis-owned host controller before these commands are retired; a staged override alone is not durable across stock CLI operations.

The host command `scripts/orbis-host-update.py` handles a digest-pinned core update on an already enrolled CLI v4.10.1 installation. It verifies the published release, takes a stopped-state checksum snapshot, and rolls back on a failed start. Synthetic beta 4 through beta 7 updates passed in the isolated arm64 VM. A restricted Unix socket host service and authenticated browser API have now been added in source. Their request and authorization tests pass, and the Update Center reviews a plan before applying it. The socket mount, process supervision, and full browser-driven transaction still need disposable-host validation before this is an installable feature. A GitHub tag alone does not mean a tested image can be installed.

## Host operating system updates

The Orbis Docker container cannot safely update the host through a general-purpose terminal or unrestricted Docker socket API. A small, separately installed host service is required. It should expose only typed operations such as list available packages, read package changelogs, stage updates, apply approved updates, read progress, and request a reboot. All mutating operations require an authenticated administrator, same-origin request protection, explicit target and package list, audit entries, and a confirmation that explains service disruption. The helper must support the host's actual package manager and reboot semantics; Hades's distribution and update method need live inventory before an adapter is chosen.

The browser should display each package's repository, installed and candidate versions, security classification when supplied by the package manager, changelog source, download size when known, reboot requirement, and a timestamp for the last successful check. Unavailable changelogs and failed checks must be labelled. Never run an opaque `curl | sh` or arbitrary browser-supplied command as an update action.

For the later multi-homelab design, the paired host agent can provide this same restricted update interface per server. The controller must show which host an update will affect and retain per-host progress and rollback records.

## Current status

The current fork preserves the existing Runtipi app update mechanisms. Its Update Center links available app updates to their real detail flows and reads published Orbis release notes directly from GitHub. Host commands cover both a guarded first stock v4.10.1 cutover and an enrolled Orbis update on a self-contained synthetic installation. The source now includes an authenticated Unix socket bridge for core updates; it stays unavailable in the UI unless the helper is connected and the enrolled image is healthy. The bridge has not yet passed a published-image browser update in the isolated VM, and real homelab data and external mounts remain unvalidated. Host operating system updates are still unimplemented.

The tag workflow builds `ghcr.io/twentylines/orbis` for amd64 and arm64, records the immutable image digest in `release-manifest.json`, and publishes notes from the matching `releases/<tag>.md` file. Repository CI and integration tests run first. Prereleases `v0.1.0-beta.1` through `v0.1.0-beta.7` have public GHCR images and attached digest manifests. A read-only release checker verifies a published GitHub tag, its attached manifest, and the exact GHCR image-index bytes and supported platforms. A separate release planner validates that manifest against a copied CLI installation and checks that a Compose image override preserves all other services and settings. A staging command can write only that generated, digest-pinned override after an operator has captured a verified snapshot. The browser reads the installed version and commit from the running container and states when the deployment did not supply an image digest. All seven published arm64 beta images were booted in a disposable CLI stack. A host command can enroll an already healthy Orbis core and start/stop that same digest with the override included. The update transaction advanced an enrolled synthetic installation from beta 4 through beta 7 with verified snapshots. The adoption transaction took a synthetic stock installation to beta 7, then restored stock after an injected post-start failure. The Unix socket browser bridge is in source but needs a published-image end-to-end rehearsal; real-data migration and external data handling remain outstanding.
